Credentials and secrets: zero tolerance

11published tutorials found with a real Blynk token, Telegram bot token or Wi-Fi password (Q4 2026 quick scan, so far)

Never publish a real password, token or key, anywhere on a tutorial page. This is the most serious rule in this guide. Anyone who copies one can take over that device, bot or account. Every rule in this section is MUST.

What counts, and the placeholder to use

Write each credential as its placeholder in code, Gists, downloads and repos. Click a placeholder to copy it.

TypeExamplesPlaceholder
Wi-FiNetwork name (SSID) and password
IoT platformBlynk auth token, template ID and name; ThingSpeak write key; Adafruit IO key
BotsTelegram bot token and chat ID
Cloud and AI servicesFirebase API key and database secret; OpenAI, Gemini or Google API keys
LoginsMQTT broker user and password, email or SMTP password, any account password
Device keysLoRaWAN AppKey, device certificates and private keys
Personal detailsPhone number, personal email, home addressLeave out, or blur in images

Where they leak

  • Gists (every old revision stays public)
  • Code typed into the page body
  • Serial Monitor screenshots
  • Blynk Console screenshots
  • BotFather chat screenshots
  • Browser address bar
  • Videos
  • ZIP and Google Drive downloads
  • GitHub repos

Rules

  1. Test with your own values on your own computer, then swap in placeholders before you copy the code anywhere. Never type a real value into the WebAdmin editor, a Gist or a repo, not even in a draft.
  2. Put a comment beside each placeholder, for example // Replace with your own Wi-Fi name, and tell the reader to replace it in a Testing & Validation step.
  3. Use a bot, Blynk device or account made only for the tutorial, never a personal or Cytron office one.
  4. Hide every credential before you save a screenshot or record a video: crop or blur the Serial Monitor, consoles, BotFather chat and the address bar (a Telegram API link contains the bot token).
  5. Before submitting, search the body, every Gist and every download for password, ssid, token, auth, key, secret, api and bot. Check any long random string that is not a placeholder.
  6. When the screenshots and video are done, revoke or regenerate the tokens you used.
  7. If a real value was ever saved in a Gist or repo, deleting it is not enough: the old revision stays public. Revoke the credential and create a new Gist.

Credential check

Paste your sketch or Gist code to look for real-looking passwords, tokens and keys. It runs in your browser only; nothing is sent or saved. It catches common patterns, so still read the code yourself.

If a real credential is already published

  1. Revoke or regenerate it the same day: /revoke in BotFather for a Telegram bot, Blynk Console for an auth token, the provider's console for an API key, or change the Wi-Fi password.
  2. Replace it with a placeholder everywhere it appears: WebAdmin body, Gist (a new one), repo, Drive file, screenshots and video.
  3. Tell your supervisor the same day. Name the page and where the credential sits, but never paste the value itself into chat, email, a report or a comment.

Removing the value without revoking it does not fix the leak: Gist revisions, Git history, search caches and readers who already copied it still hold it. Only revoking makes it useless.

01

Get access and create the post

Every tutorial is written and published in WebAdmin. Set up the post before you write a word.

  1. Ask your supervisor to set up your WebAdmin username. Every supervisor can do this. Choose a short username, not your full name as it appears on your IC.
  2. Open cytron.io/admin and log in with your username. The first time, use Forgot Password to set your password.
  3. Expand the Tutorial tab on the left and select Tutorials, then click + to create a new post.
  4. In the Data tab, set the SEO URL first. It also names the folder your images upload into.
  5. Fill every field in the General, Data, Links and Image tabs (step 02).
  6. Write the body in the Description field, following the structure in step 03.
  7. Click Save every time you make a change.

Fill every field before writing the body. Every field below is MUST.

All SEO fields are compulsory. A tutorial with an empty or incomplete SEO field is not ready to publish.

e.g.ESP32 High Temperature Alert System

03

Write the tutorial

Write the body in the Description field. Write for complete beginners, in clear, simple language, with active voice and short sentences. MUST

3.1Required structure

Every tutorial uses these headings, in this order, worded exactly as shown. The page title is set in Post Name and never repeated in the body, so the body starts at H2. No H1 in the body, no empty headings.

  1. 01IntroductionH2MUST2 to 4 sentences: what the reader builds and why it matters for Education or Industry use. Open with the reader's problem. Right after the paragraph, put the video tutorial if there is one, or an optional hero image.
  2. 02Disclaimer / Safety NotesH2IF APPLICABLEElectrical, battery or heat cautions, warranty notes, classroom supervision. See Safety notes.
  3. 03PrerequisitesH2MUSTLink the Getting Started guides or basics to finish first. Name the software, accounts, firmware or SDKs to install.
  4. 04ObjectivesH2MUSTOne paragraph only.
  5. 05List of ComponentsH2MUSTNumbered list, [Product name] x1, name linked, opens in a new window. Name and link only, no product pictures. See Components & links.
  6. 06System Diagram & WiringH2MUSTA block or circuit diagram (Canva, Fritzing) at its native aspect ratio, plus a pin-to-pin wiring table: [Board], [Module], Function. Add a Note: for mounting tips or other ways to connect.
  7. 07Software SetupH2MUSTIDE or toolchain version, library names with install steps, board and port selection. Link the official download or documentation page of every software. Screenshots encouraged.
  8. 07aInstall [Library name] LibraryH3IF A LIBRARYNumbered Library Manager steps, including the "Install All" dependency prompt.
  9. 08Sample CodeH2MUST"Upload the following sketch to your Maker ESP32:" then a public GitHub Gist embed.
  10. 08aKey Code ExplanationH3MUSTBrief explanation of the key blocks: one bullet per line, code: what it does.
  11. 09Testing & ValidationH2MUSTNumbered steps to run and verify. Put a short troubleshooting note inline where a step often fails.
  12. 09aExpected ResultsH3MUSTExpected outputs: Serial Monitor lines, LEDs, sounds, browser view.
  13. 10Demo / ResultsH2MUSTPhotos or a YouTube embed of the working project, and screenshots of dashboards or the Serial Monitor.
  14. 11Troubleshooting & Extra TipsH2MUST3 to 4 H3s, each a symptom as the reader sees it, with bullet fixes: power, baud rate, library conflicts, sensor orientation, calibration.
  15. 12ConclusionH2MUST2 to 3 sentences: what the reader built and learned, the final result, and what to try next (link a related tutorial).
  16. 13Downloads & AssetsH2IF APPLICABLEZIP of diagrams or configs, repo links, datasets, example flows, STL or 3D files.
  17. 14Telegram community bannerno headingMUSTOne banner at the very end, centred, 900 px wide, linked to the matching community. See Telegram banner.

The Hardware Components block and Related Posts below the body come from the Related Product, Parent and Related Post fields in the Links tab, not from the body.

Copy-ready skeleton

Paste this into the editor's Source view, then replace every [bracket] and comment. Delete Disclaimer / Safety Notes or Downloads & Assets only if they don't apply.


      


      
3.2Formatting and layout

      
Most review comments are about how the page looks, not what it says. Every rule here is MUST: check each one in the editor, then again on the live page after publishing.

      

        
AreaRule

        
          
AlignmentJustify every paragraph, the Introduction included.

          
FontThe editor's default font and size only. Never set another font or sizes such as 16 or 20. Copying from Word, Google Docs, ChatGPT or a website? Use Paste as plain text so the old formatting doesn't come along.

          
HeadingsEvery section title is a Heading 2; sub-titles inside it are Heading 3. Never use bold text as a heading, and don't bold a heading (it is already bold), Troubleshooting H3s included. Title case, not capitals: "Introduction", not "INTRODUCTION".

          
Start of the bodyStart straight with the Introduction heading: no page title, horizontal line or picture before it. Prerequisites gets its own Heading 2, separate from the Introduction.

          
SpacingOne empty line between paragraphs, between text and a picture, between two pictures, and between code and a picture. Nothing touches or overlaps.

          
PicturesInsert through Browse Server only, saved as PNG or JPEG. Never paste a picture copied from Google Docs, Word or a website: it keeps an outside link (such as googleusercontent.com) and breaks into a red X. 800 px wide at most: resize wider pictures with the ratio lock on, and never enlarge narrower ones. No stretched or blurred pictures. No picture of code that is already on the page as text.

          
LinksEvery link opens in New Window (_blank).

          
BannerOne Telegram banner at the very end: centred, 900 px wide, linked to its community in a New Window (_blank). Steps in Editor how-tos.

          
LengthIf the tutorial is too long, split it into a series: set Parent in the Links tab and number the parts in Sort Order.

3.5Code, versions and setup

      
A reader must be able to rebuild the project months later, so tested versions are named and every file lives where Cytron controls it.

      
    
        
  • MUST
    Long code: a public GitHub Gist. Staff use their own GitHub account. Interns use the intern GitHub account; ask your supervisor for access, and Mat Liven for the authentication code. Never use the account of someone outside Cytron.
    • 
        
  • MUST
    Short command lines: the editor's Computer Code style. Use Shift+Enter for a new line, or each line lands in its own box.
    • 
        
  • MUST
    State the IDE or toolchain version and the board package, e.g. "esp32 by Espressif Systems 3.3.12". Library versions SHOULD be named too.An unpinned core caused ledcAttach compile errors for readers on core 2.x.
    • 
        
  • SHOULD
    Open the sketch with a header comment: project, board (Cytron Maker ESP32) and main module.
    • 
        
  • MUST
    Placeholders, never real credentials: YOUR_WIFI_SSID, YOUR_WIFI_PASSWORD. Tell the reader to replace them in a Testing & Validation step. Full rules in Credentials.
    • 
        
  • MUST
    Code is text, never a screenshot. Terminal and Serial Monitor output can be a screen capture under Demo / Results.
    • 
        
  • SHOULD
    Name built-in libraries: when WiFi.h or WebServer.h need no install, say so in Software Setup.
    • 
        
  • MUST
    Quote error messages literally as the Troubleshooting H3.e.g. Serial Monitor shows "Failed to read from DHT sensor!"
    • 
        
  • MUST
    Proofread and test it yourself: follow your own tutorial on a clean setup before submitting. Peer review is recommended.

3.7Safety notes and disclaimers

      
Add the Disclaimer / Safety Notes section directly after the Introduction when any trigger below applies. Including it even for low-risk builds is good practice. Open with "This project is an educational prototype designed for learning…", then name the concrete risk and the precaution. A generic "be careful" does not count.

      

        
TriggerWhat the note must say

        
          
Mains ACOnly qualified people wire mains (relays switching 230 V, power supplies); use an enclosed, rated relay module; unplug before touching.

          
LiPo or Li-ion batteriesCorrect polarity, no short circuits, never charge unattended.

          
Motors, servos, robotsKeep fingers clear of moving parts; the code includes a stop-on-disconnect failsafe.

          
Soldering or heatVentilation and eye protection.

          
Food, pets or peopleFood-grade materials for food contact; someone checks in person if the device fails.

          
Alarms, gas, fire, temperature, medical"Educational prototype, not a certified safety device."

          
5 V sensors on 3.3 V pinsUse a level shifter or divider; state the pin voltage.

          
Passwords, bot tokens, API keysKeep them private; never publish code containing real credentials (see Credentials).

        
      

      
Also add warranty notes where a build could void one (modifying a board, overdriving a motor), and state that adult supervision is required when the tutorial is meant for classroom use.
